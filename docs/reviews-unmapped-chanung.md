## 1. 사과 먹기 게임 — 대표 풀이

**파일**: `안찬웅/week6/사과 먹기 게임.java` / **컴파일**: 통과 / **판정**: needs-fix

### 접근

목표 숫자를 1부터 차례로 밟아야 하고 **회전할 때마다 비용 1, 전진은 비용 0** 이라는 구조를
정확히 읽고 **0-1 BFS** 를 골랐다. 이 선택이 이 풀이의 핵심이고 맞다.

```java
// 전진 (비용 0)
if(... && cnt < dist[nx][ny][dir]) { dist[nx][ny][dir] = cnt; q.offerFirst(...); }
// 우회전 (비용 1)
if(cnt + 1 < dist[r][c][nd]) { dist[r][c][nd] = cnt + 1; q.offerLast(...); }
```

상태를 `(r, c, dir)` 3차원으로 잡고 `dist[n][n][4]` 로 관리한 것, 비용 0 은 `offerFirst`,
비용 1 은 `offerLast` 로 나눈 것, 꺼낼 때 `cnt > dist[r][c][dir]` 로 낡은 항목을 버리는 것 —
0-1 BFS 의 세 가지 요건이 다 들어가 있다. 다익스트라를 우선순위 큐로 쓰면 `log` 가 붙는데
여기서는 붙지 않는다.

목표를 1 → 2 → … 로 하나씩 끊어 풀고, 도착 상태 `(r, c, dir)` 를 다음 BFS 의 시작 상태로
넘기는 것도 맞다. **방향까지 넘기지 않으면** 다음 구간의 첫 회전 비용을 놓친다.

### 개선점

#### 1. (치명) 출력 형식에 `#{테스트케이스}` 가 없다

```java
sb.append(dirCnt).append("\n");
```

같은 회차의 다른 SWEA 풀이(`벌꿀채취.java`, `핀볼게임.java`)는 전부
`sb.append("#").append(test_case).append(" ")` 로 시작한다. 이 파일만 답만 찍는다.
같은 폴더의 `면접 실패.java` 는 `#` 를 붙이고 있어서, 두 문제의 출력 형식이 다르다고 볼 근거가
없다면 이건 빠뜨린 것이다. **→ 문제 페이지에서 출력 형식 확인 필요.**

#### 2. (치명) `package algorithm;` 이 붙어 있다

SWEA 는 **default package** 의 `public class Solution` 을 요구한다. 패키지 선언이 있으면
제출 자체가 안 된다. 클래스명이 `Solution` 인 건 맞으니 첫 줄만 지우면 된다.
(`핀볼게임.java` 도 같은 이유로 `package practive;` 를 이번에 걷어냈다.)

#### 3. (중요) 우회전만 있고 좌회전이 없다

```java
int nd = (dir + 1) % 4;   // 우회전 하나만
```

주석에도 "우회전 1" 이라고 적혀 있어 의도한 것으로 보이지만, 이 경우 **왼쪽으로 도는 데 비용 3**
이 든다. 문제가 "회전할 때마다 1" 이라면 좌회전도 비용 1 이어야 하고, 그러면 답이 달라진다.
**→ 규칙 확인 필요.** 좌회전도 비용 1 이면 한 줄만 늘리면 된다.

```java
for (int t = 1; t <= 3; t += 2) {          // 우회전, 좌회전
    int nd = (dir + t) % 4;
    if (cnt + 1 < dist[r][c][nd]) { dist[r][c][nd] = cnt + 1; q.offerLast(new int[]{r, c, nd, cnt + 1}); }
}
```

#### 4. (중요) 목표 숫자를 못 찾으면 조용히 넘어간다

```java
return new int[]{x, y, d, 0};   // bfs 가 target 을 못 찾았을 때
```

시작 위치·방향을 그대로, 비용 0 으로 돌려준다. 즉 **도달 불가능한 케이스가 "비용 0으로 도착"
으로 둔갑**한다. `maxNum` 을 격자에 있는 최댓값으로 잡기 때문에 1~maxNum 중간에 빠진 숫자가
있으면 여기 걸린다. 못 찾은 것은 못 찾았다고 구분해야 디버깅이 된다.

#### 5. (중요) `dist` 를 목표마다 새로 만든다

```java
static int[] bfs(...) {
    dist = new int[n][n][4];
    for(...) Arrays.fill(dist[i][j], Integer.MAX_VALUE);
```

목표 숫자 개수만큼 `n × n × 4` 배열을 새로 할당하고 채운다. `n` 과 목표 수가 커지면
이 초기화가 탐색보다 오래 걸릴 수 있다. 배열은 한 번만 만들고 `Arrays.fill` 로 재사용하거나,
`int[][][] stamp` 에 "몇 번째 탐색에서 쓴 값인지"를 같이 적어 두면 초기화 없이 재사용된다.

#### 6. (사소) 입력 읽기가 줄 길이에 의존한다

```java
String str = br.readLine();
for(int j=0; j<str.length(); j++) { ... }
```

한 줄이 붙어 있는 숫자 문자열이라는 가정이다. 공백으로 나뉘어 들어오면 그대로 깨진다.
`n` 만큼 도는 것이 안전하다 — 실제 입력 형식을 확인해 맞춰 둘 것.

### 복잡도

- 시간: `O(목표 수 × n^2 × 4)` — 목표마다 0-1 BFS 한 번. 우선순위 큐가 아니라 `log` 는 없다.
- 공간: `O(n^2 × 4)` — `dist`.

### 요약

**알고리즘 선택이 정확하고 0-1 BFS 구현도 정석대로다.** 남은 문제는 알고리즘이 아니라
제출 형식(패키지, `#` 출력)과 회전 규칙 확인이다. 형식 두 개는 지금 바로 고칠 수 있고,
회전 규칙만 확인되면 이 풀이는 그대로 통과할 모양이다.

## 2. 사과 먹기 게임 — 실패 기록

**파일**: `안찬웅/week6/사과 먹기 게임 실패.java` / **판정**: wrong

### 왜 실패했나 — 대표 풀이와 무엇이 달랐나

이 파일과 위 대표 풀이의 차이는 **"상태를 어디에 두었는가"** 하나로 요약된다.

| | 실패 버전 | 대표 풀이 |
| --- | --- | --- |
| 방문 관리 | `boolean[n][n][4] vis` | `int[n][n][4] dist` (비용) |
| 목표 진행 | `static int num` 을 BFS 안에서 `num++` | 목표마다 BFS 를 다시 시작 |
| 회전 비용 | 없음 | 우회전 = 비용 1 |
| 큐 | 일반 `Queue` | `Deque` + offerFirst/offerLast |

**핵심**: `boolean vis` 로는 이 문제를 풀 수 없다. 같은 칸·같은 방향이라도 **몇 번 회전해서
왔는지**가 다르면 이후 최적값이 달라진다. "방문했는가"가 아니라 "몇 번에 왔는가"를 들고 있어야
하고, 그 순간 자료구조는 `boolean` 이 아니라 `int dist` 가 된다. 대표 풀이는 이 전환을 해냈다.

### 그 외 실제 결함

1. **(치명) `bfs` 가 한 번도 호출되지 않는다.** `main` 은 격자를 읽고 `num = 1;` 한 뒤
   `sb.append(num)` 을 찍는다. **어떤 입력에도 `1` 만 출력한다.**
2. **(치명) `maxNum` 이 테스트케이스마다 초기화되지 않는다.** `static int maxNum;` 이
   루프 밖에서 한 번만 0 이라, 두 번째 케이스부터는 이전 케이스의 최댓값이 남아 `endX/endY`
   갱신이 안 된다. **static 필드는 케이스 시작마다 리셋한다** — 멀티 테스트케이스 문제의
   1번 함정이다.
3. **(치명) `num++` 을 BFS 안에서 한다.** 큐에 여러 갈래가 동시에 들어 있는데 전역 카운터를
   증가시키면, 어느 갈래가 먼저 처리되느냐에 따라 목표가 제멋대로 앞당겨진다.
   목표 진행은 BFS 밖에서 관리해야 한다 — 대표 풀이가 그렇게 고쳤다.
4. **(치명) 디버그 출력이 루프 안에 있다.** `System.out.println("nx: " + nx + " ny: " + ny)` 는
   채점 출력에 그대로 섞인다. 알고리즘이 맞아도 오답 처리된다.
5. **(중요) `vis[nx][ny][(dir + 1) % 4] = true;` 뒤에 그 방향으로 큐에 넣지 않는다.**
   방문 표시만 하고 갈래를 만들지 않으니, 회전한 경로가 아예 탐색되지 않는다.

### 이 파일에서 가져갈 것

주석에 적은 계획(`1.1 가장 큰 수의 인덱스를 만나면 return` / `1.2 1을 향해 이동하면서 방향을
회전할때마다 카운팅`)이 이미 문제를 정확히 요약하고 있다. **막힌 지점은 "회전 비용을 어떻게
셀 것인가"였고, 그 답이 가중치 0/1 그래프**라는 것을 알아챈 순간 대표 풀이가 나왔다.
"비용이 0 과 1 뿐이면 0-1 BFS" 는 한 번 외워 두면 계속 쓰는 패턴이다.

## 3. 면접 — 실패 기록

**파일**: `안찬웅/week6/면접 실패.java` / **컴파일**: 통과 / **판정**: needs-fix (규칙 확인 필요)

### 접근

n문제 중 m개를 맞췄을 때 총점이 **최소**가 되는 배치를 직접 구성하고, 그 배치를 문제 규칙대로
한 번 시뮬레이션한다. 관찰 세 개가 들어가 있고 셋 다 방향이 맞다.

1. **틀린 문제(X)는 연속 카운터를 끊는 칸막이다.** → 맞은 문제를 여러 덩어리로 쪼갤 수 있다.
2. **덩어리 하나에 `k-1` 개까지는 2배가 안 터진다.** → 정원 `group × (k-1)`.
3. **2배는 그 시점까지의 누적 점수를 곱한다.** → 2배가 **작은 점수에 걸리도록 앞쪽에 몰아야** 한다.

3번이 특히 좋다. 최소화 문제에서 "곱셈은 값이 작을 때 당해야 유리하다" 를 정확히 짚었다.
검증 삼아 `m=4, k=2, wrong=1` 을 손으로 돌려 봤다.

```
OOO X O  ->  1, 2(*2=4), 5, X, 6      = 6   (이 코드의 배치)
O X OOO  ->  1, X, 2, 3(*2=6), 7      = 7
OO X OO  ->  1, 2(*2=4), X, 5, 6(*2=12) = 12
```

앞쪽에 몰아넣는 쪽이 실제로 최소다.

### 개선점

#### 1. (치명) 그리디가 최적이라는 증명이 없다 — 이 부분이 "실패"의 원인일 가능성이 높다

세 관찰은 각각 그럴듯하지만, **"덩어리 개수를 최대로 + 초과분은 맨 앞 덩어리에 전부"** 가
언제나 최소라는 보장은 없다. 특히 초과분이 클 때 첫 덩어리에서 2배가 여러 번 연속으로
터지는데, 그걸 두 덩어리에 나누는 편이 나은 구간이 있을 수 있다.

**확인 방법이 있다.** n 이 작을 때(예: n ≤ 12) 모든 O/X 배치를 완전탐색해서 최소 점수를 구하고,
이 그리디 결과와 무작위로 수천 건 대조하면 반례가 있는지 바로 나온다. 반례가 안 나오면
그리디를 믿고 쓰고, 나오면 그 반례가 곧 올바른 배치의 힌트가 된다.
`claude.md` 의 "수정안은 검증하고 쓴다" 원칙이 이 상황을 위해 있다.

```java
// 검증용 완전탐색 (제출용 아님)
static int brute(int n, int m, int k) {
    int best = Integer.MAX_VALUE;
    for (int mask = 0; mask < (1 << n); mask++) {
        if (Integer.bitCount(mask) != m) continue;
        int cnt = 0, score = 0;
        for (int i = 0; i < n; i++) {
            if ((mask & (1 << i)) == 0) { cnt = 0; continue; }
            cnt++; score++;
            if (cnt == k) { score *= 2; cnt = 0; }
        }
        best = Math.min(best, score);
    }
    return best;
}
```

#### 2. (중요) 점수가 int 를 넘길 수 있다

`score *= 2` 가 반복되면 지수적으로 커진다. 2배가 31번만 일어나도 int 를 넘긴다.
n 이 조금만 커져도 위험하다. **→ 문제의 n·k 제약 확인 필요.** 제약에 따라 `long` 이나
모듈러 연산이 필요할 수 있다.

#### 3. (중요) `k == 1` 일 때의 동작을 확인해야 한다

`cap = group * (k - 1)` 이 0 이 되어 `over = m`, 즉 전부 첫 덩어리로 몰린다.
`calcScore` 는 맞은 문제마다 바로 2배를 하므로 계산 자체는 성립하지만,
이때 배치가 답에 영향을 주지 않는다는 점(어디에 두든 2배 횟수가 m 으로 같다)을
알고 넘어가는 것과 모르고 넘어가는 것은 다르다.

#### 4. (사소) `build()` 의 인덱스 안전성

`idx` 가 `n` 을 넘지 않는 것은 `group ≤ wrong + 1` 과 `m + wrong = n` 에서 따라 나온다.
지금 코드는 맞지만 **왜 안전한지가 코드에 안 드러난다.** 덩어리 수와 칸막이 수의 관계를
한 줄 계산으로 뽑아 두면 이후에 조건을 건드릴 때 깨지지 않는다.

#### 5. (사소) 미사용 변수

`StringTokenizer st` 를 선언만 하고 `st = new StringTokenizer(...)` 로 매 케이스 재할당하는데,
`minScore = 0;` 초기화는 바로 뒤 `minScore = calcScore();` 에 덮여서 의미가 없다.

### 복잡도

- 시간: `O(T · n)` — 케이스마다 배치 구성 한 번, 시뮬레이션 한 번. 매우 빠르다.
- 공간: `O(n)`

### 요약

**틀린 문제를 칸막이로 본 것, 2배를 작은 점수에 걸리게 앞으로 몰아야 한다고 본 것** — 관찰
자체는 이 문제의 정답 방향이다. 실패한 이유는 아이디어가 아니라 **그 그리디를 검증하지 않고
바로 제출한 것**일 가능성이 높다. 위 완전탐색 조각을 붙여 작은 n 에서 대조하면 15분 안에
맞는지 틀린지 결론이 난다. 그리디는 "그럴듯함" 과 "맞음" 의 거리가 가장 먼 유형이라,
**작은 입력 완전탐색 대조는 그리디를 낼 때마다 붙이는 습관으로 두는 게 좋다.**
