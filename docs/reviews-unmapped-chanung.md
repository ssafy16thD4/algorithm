## 1. 사과 먹기 게임 — 대표 풀이

**파일**: `안찬웅/week6/사과 먹기 게임.java` / **컴파일**: 통과 / **판정**: good (회전 규칙만 확인 필요)

### 접근

목표 숫자를 1부터 차례로 밟아야 하고 **회전할 때마다 비용 1, 전진은 비용 0** 이라는 구조를
정확히 읽고 **0-1 BFS** 를 골랐다. 이 선택이 이 풀이의 핵심이고 맞다.

```java
// 전진 (비용 0)
if(... && cnt < dist[nx][ny][dir]) { dist[nx][ny][dir] = cnt; q.offerFirst(...); }
// 우회전 (비용 1)
if(cnt + 1 < dist[r][c][nd]) { dist[r][c][nd] = cnt + 1; q.offerLast(...); }
```

상태를 `(r, c, dir)` 3차원으로 잡고 `dist[n][n][4]` 로 관리한 것, 비용 0 은 `offerFirst`,
비용 1 은 `offerLast` 로 나눈 것, 꺼낼 때 `cnt > dist[r][c][dir]` 로 낡은 항목을 버리는 것 —
0-1 BFS 의 세 가지 요건이 다 들어가 있다. 다익스트라를 우선순위 큐로 쓰면 `log` 가 붙는데
여기서는 붙지 않는다.

목표를 1 → 2 → … 로 하나씩 끊어 풀고, 도착 상태 `(r, c, dir)` 를 다음 BFS 의 시작 상태로
넘기는 것도 맞다. **방향까지 넘기지 않으면** 다음 구간의 첫 회전 비용을 놓친다.

**실제로 돌려본 검증 (2026-09-08 추가)**: "(0,0) 우향 시작 · 전진 0 · 시계 방향 회전 1 · 사과 번호 순서" 모델로
전 단계를 한 번에 푸는 다익스트라(상태 = 사과 번호 × 칸 × 방향)를 독립적으로 짜서 무작위 1,500건과 대조해
**불일치 0건**. 같은 모델로 돌린 이성일 풀이는 252건, 김준수 실패 버전은 1,048건이 어긋났다 — 세 사람 중 이 풀이만 맞았다.
단계마다 BFS 를 끊어도 되는 이유는 도착 상태에 방향이 포함돼 있어서다. 방향까지 같이 넘기면 다음 단계의
시작 상태가 하나로 정해져도 전역 최적을 놓치지 않는다.

### 개선점

#### 1. (치명) 출력 형식에 `#{테스트케이스}` 가 없다

```java
sb.append(dirCnt).append("\n");
```

같은 회차의 다른 SWEA 풀이(`벌꿀채취.java`, `핀볼게임.java`)는 전부
`sb.append("#").append(test_case).append(" ")` 로 시작한다. 이 파일만 답만 찍는다.
같은 폴더의 `면접 실패.java` 는 `#` 를 붙이고 있어서, 두 문제의 출력 형식이 다르다고 볼 근거가
없다면 이건 빠뜨린 것이다. **→ 문제 페이지에서 출력 형식 확인 필요.**

#### 2. (중요) 우회전만 있고 좌회전이 없다

```java
int nd = (dir + 1) % 4;   // 우회전 하나만
```

주석에도 "우회전 1" 이라고 적혀 있어 의도한 것으로 보이지만, 이 경우 **왼쪽으로 도는 데 비용 3**
이 든다. 문제가 "회전할 때마다 1" 이라면 좌회전도 비용 1 이어야 하고, 그러면 답이 달라진다.
**→ 규칙 확인 필요.** 좌회전도 비용 1 이면 한 줄만 늘리면 된다.

```java
for (int t = 1; t <= 3; t += 2) {          // 우회전, 좌회전
    int nd = (dir + t) % 4;
    if (cnt + 1 < dist[r][c][nd]) { dist[r][c][nd] = cnt + 1; q.offerLast(new int[]{r, c, nd, cnt + 1}); }
}
```

#### 3. (중요) 목표 숫자를 못 찾으면 조용히 넘어간다

```java
return new int[]{x, y, d, 0};   // bfs 가 target 을 못 찾았을 때
```

시작 위치·방향을 그대로, 비용 0 으로 돌려준다. 즉 **도달 불가능한 케이스가 "비용 0으로 도착"
으로 둔갑**한다. `maxNum` 을 격자에 있는 최댓값으로 잡기 때문에 1~maxNum 중간에 빠진 숫자가
있으면 여기 걸린다. 못 찾은 것은 못 찾았다고 구분해야 디버깅이 된다.

#### 4. (중요) `dist` 를 목표마다 새로 만든다

```java
static int[] bfs(...) {
    dist = new int[n][n][4];
    for(...) Arrays.fill(dist[i][j], Integer.MAX_VALUE);
```

목표 숫자 개수만큼 `n × n × 4` 배열을 새로 할당하고 채운다. `n` 과 목표 수가 커지면
이 초기화가 탐색보다 오래 걸릴 수 있다. 배열은 한 번만 만들고 `Arrays.fill` 로 재사용하거나,
`int[][][] stamp` 에 "몇 번째 탐색에서 쓴 값인지"를 같이 적어 두면 초기화 없이 재사용된다.

#### 5. (사소) 입력 읽기가 줄 길이에 의존한다

```java
String str = br.readLine();
for(int j=0; j<str.length(); j++) { ... }
```

한 줄이 붙어 있는 숫자 문자열이라는 가정이다. 공백으로 나뉘어 들어오면 그대로 깨진다.
`n` 만큼 도는 것이 안전하다 — 실제 입력 형식을 확인해 맞춰 둘 것.

### 복잡도

- 시간: `O(목표 수 × n^2 × 4)` — 목표마다 0-1 BFS 한 번. 우선순위 큐가 아니라 `log` 는 없다.
- 공간: `O(n^2 × 4)` — `dist`.

### 요약

**알고리즘 선택이 정확하고 0-1 BFS 구현도 정석대로다.** 무작위 1,500건 대조에서 전부 정답이고,
같은 문제를 푼 다른 두 풀이는 여기서 갈렸다. 남은 건 좌회전도 비용 1 인지, 출력에 `#tc` 가 필요한지
두 가지 확인뿐이다.

## 2. 사과 먹기 게임 — 실패 기록

**파일**: `안찬웅/week6/사과 먹기 게임 실패.java` / **판정**: wrong

### 왜 실패했나 — 대표 풀이와 무엇이 달랐나

이 파일과 위 대표 풀이의 차이는 **"상태를 어디에 두었는가"** 하나로 요약된다.

| | 실패 버전 | 대표 풀이 |
| --- | --- | --- |
| 방문 관리 | `boolean[n][n][4] vis` | `int[n][n][4] dist` (비용) |
| 목표 진행 | `static int num` 을 BFS 안에서 `num++` | 목표마다 BFS 를 다시 시작 |
| 회전 비용 | 없음 | 우회전 = 비용 1 |
| 큐 | 일반 `Queue` | `Deque` + offerFirst/offerLast |

**핵심**: `boolean vis` 로는 이 문제를 풀 수 없다. 같은 칸·같은 방향이라도 **몇 번 회전해서
왔는지**가 다르면 이후 최적값이 달라진다. "방문했는가"가 아니라 "몇 번에 왔는가"를 들고 있어야
하고, 그 순간 자료구조는 `boolean` 이 아니라 `int dist` 가 된다. 대표 풀이는 이 전환을 해냈다.

### 그 외 실제 결함

1. **(치명) `bfs` 가 한 번도 호출되지 않는다.** `main` 은 격자를 읽고 `num = 1;` 한 뒤
   `sb.append(num)` 을 찍는다. **어떤 입력에도 `1` 만 출력한다.**
2. **(치명) `maxNum` 이 테스트케이스마다 초기화되지 않는다.** `static int maxNum;` 이
   루프 밖에서 한 번만 0 이라, 두 번째 케이스부터는 이전 케이스의 최댓값이 남아 `endX/endY`
   갱신이 안 된다. **static 필드는 케이스 시작마다 리셋한다** — 멀티 테스트케이스 문제의
   1번 함정이다.
3. **(치명) `num++` 을 BFS 안에서 한다.** 큐에 여러 갈래가 동시에 들어 있는데 전역 카운터를
   증가시키면, 어느 갈래가 먼저 처리되느냐에 따라 목표가 제멋대로 앞당겨진다.
   목표 진행은 BFS 밖에서 관리해야 한다 — 대표 풀이가 그렇게 고쳤다.
4. **(치명) 디버그 출력이 루프 안에 있다.** `System.out.println("nx: " + nx + " ny: " + ny)` 는
   채점 출력에 그대로 섞인다. 알고리즘이 맞아도 오답 처리된다.
5. **(중요) `vis[nx][ny][(dir + 1) % 4] = true;` 뒤에 그 방향으로 큐에 넣지 않는다.**
   방문 표시만 하고 갈래를 만들지 않으니, 회전한 경로가 아예 탐색되지 않는다.

### 이 파일에서 가져갈 것

주석에 적은 계획(`1.1 가장 큰 수의 인덱스를 만나면 return` / `1.2 1을 향해 이동하면서 방향을
회전할때마다 카운팅`)이 이미 문제를 정확히 요약하고 있다. **막힌 지점은 "회전 비용을 어떻게
셀 것인가"였고, 그 답이 가중치 0/1 그래프**라는 것을 알아챈 순간 대표 풀이가 나왔다.
"비용이 0 과 1 뿐이면 0-1 BFS" 는 한 번 외워 두면 계속 쓰는 패턴이다.

## 3. 면접 — 실패 기록

**파일**: `안찬웅/week6/면접 실패.java` / **컴파일**: 통과 / **판정**: good (완전탐색 728건 검증, 점수 자료형만 확인 필요)

### 접근

n문제 중 m개를 맞췄을 때 총점이 **최소**가 되는 배치를 직접 구성하고, 그 배치를 문제 규칙대로
한 번 시뮬레이션한다. 관찰 세 개가 들어가 있고 셋 다 방향이 맞다.

1. **틀린 문제(X)는 연속 카운터를 끊는 칸막이다.** → 맞은 문제를 여러 덩어리로 쪼갤 수 있다.
2. **덩어리 하나에 `k-1` 개까지는 2배가 안 터진다.** → 정원 `group × (k-1)`.
3. **2배는 그 시점까지의 누적 점수를 곱한다.** → 2배가 **작은 점수에 걸리도록 앞쪽에 몰아야** 한다.

3번이 특히 좋다. 최소화 문제에서 "곱셈은 값이 작을 때 당해야 유리하다" 를 정확히 짚었다.
검증 삼아 `m=4, k=2, wrong=1` 을 손으로 돌려 봤다.

```
OOO X O  ->  1, 2(*2=4), 5, X, 6      = 6   (이 코드의 배치)
O X OOO  ->  1, X, 2, 3(*2=6), 7      = 7
OO X OO  ->  1, 2(*2=4), X, 5, 6(*2=12) = 12
```

앞쪽에 몰아넣는 쪽이 실제로 최소다.

### 개선점

#### 1. (해결) 그리디가 최적인지 완전탐색으로 확인했다 — 맞다

이 리뷰의 초안은 "그리디 증명이 없으니 작은 n 완전탐색으로 대조하라" 였다. **2026-09-08 에 실제로 돌렸다.**
`n ≤ 12` 의 모든 `(n, m, k)` 조합 728건을 O/X 전 배치 완전탐색과 대조해 **불일치 0건**.
이성일의 대표 풀이(`이성일/week6/면접.java`)도 같은 728건에서 0건이다.
즉 **이 파일의 그리디는 정답이고, "실패" 의 원인은 배치 전략이 아니다.**

#### 2. (중요) 점수가 int 를 넘길 수 있다 — 제약 확인 필요

`score *= 2` 가 반복되면 지수적으로 커진다. 2배가 31번만 일어나도 int 를 넘긴다. n 이 조금만 커져도 위험하다.
**→ 문제의 n·k 제약 확인 필요.** 제약에 따라 `long` 이나 모듈러 연산이 필요하고, 시험에서 틀렸다면
지금 남은 후보 중에서는 이 지점이 가장 유력하다.

### 복잡도

- 시간: `O(T · n)` — 케이스마다 배치 구성 한 번, 시뮬레이션 한 번. 매우 빠르다.
- 공간: `O(n)`

### 요약

**틀린 문제를 칸막이로 본 것, 2배를 작은 점수에 걸리게 앞으로 몰아야 한다고 본 것** — 관찰이 맞았고
완전탐색 728건이 그것을 확인해 줬다. 알고리즘은 정답이다. 실패했다면 점수 자료형(int 초과)이나 입력 형식을
먼저 의심할 것. 그리디를 낼 때 **작은 입력 완전탐색 대조**를 붙이는 습관은 그대로 유효하다 —
이번엔 그게 "맞다" 를 15분 만에 증명했다.

## 4. 14기 3차 1번 — 대표 풀이

**파일**: `안찬웅/week6/14기 3차 1번.java` / **컴파일**: 통과 / **판정**: needs-fix (제약 확인 필요)

SSAFY 14기 3차 A형 시험 1번으로 보인다. 공개 문제 페이지가 없어 `problems.json` 에 못 넣었다.
주석대로 **"길이 K 인 연속 부분 수열 두 개를 겹치지 않게 골라 합을 최대로"** 로 읽고 리뷰했다.

### 접근

두 단계다. 먼저 모든 시작점 `i` 의 K칸 합 `arrSum[i]` 를 만들고, 그다음 `j ≥ i+K` 인 쌍
`(i, j)` 를 전부 돌며 `arrSum[i] + arrSum[j]` 의 최댓값을 잡는다. "겹치지 않음 = 두 번째 시작점이
첫 번째 시작점 + K 이상" 이라는 조건을 `j = i+k` 한 줄로 정확히 옮겼다.

**실제로 돌려본 검증**: 삼중 루프 완전탐색과 무작위 900건(`N ≤ 20`, 값 −50~50)을 대조해
**불일치 0건**. 답은 맞는다.

### 개선점

#### 1. (중요) 쌍 열거가 O(N²) 이라 N 이 커지면 시간초과 — 누적합 + 접미사 최댓값으로 O(N)

`arrSum` 을 만드는 데 `O(N·K)`, 쌍을 도는 데 `O(N²)` 이다. **N 제약을 확인하지 못했지만**
실측하면 감이 온다.

| N | K | 원본 | 아래 수정안 |
| --- | --- | --- | --- |
| 100,000 | 1,000 | 2.0초 | 0.1초 |
| 300,000 | 1,000 | 34.4초 | 0.1초 |

N 이 수천이면 문제없고, 10⁵ 급이면 못 쓴다. 시험 1번에서 N 이 작았다면 이 코드로 통과했을 것이고,
컸다면 이 지점이 원인이다. 어느 쪽이든 **O(N) 풀이가 더 짧으므로** 그쪽을 기본형으로 두는 게 낫다.

핵심은 두 가지. 구간 합은 누적합으로 O(1) 에 뽑고, "`j ≥ i+K` 중 최대" 는 **뒤에서부터 접미사
최댓값** 을 한 번 만들어 두면 `i` 마다 O(1) 이다.

```java
long[] pre = new long[n + 1];
for (int i = 0; i < n; i++) pre[i + 1] = pre[i] + arr[i];

int w = n - k + 1;                       // 시작점 개수
long[] win = new long[w];
for (int i = 0; i < w; i++) win[i] = pre[i + k] - pre[i];

long[] sufMax = new long[w + 1];         // sufMax[i] = max(win[i..w-1])
sufMax[w] = Long.MIN_VALUE / 4;
for (int i = w - 1; i >= 0; i--) sufMax[i] = Math.max(win[i], sufMax[i + 1]);

long best = Long.MIN_VALUE;
for (int i = 0; i + k < w; i++) best = Math.max(best, win[i] + sufMax[i + k]);
```

**검증함** — 위 코드를 원본·완전탐색과 같은 900건에 대조해 불일치 0건, 위 표의 시간도 이 코드로 잰 것이다.

#### 2. (중요) 합이 `int` 를 넘길 수 있다 — 값 범위 확인 필요

`sum` 과 `twoSum` 이 `int` 다. 원소가 10⁹ 급이면 K=3 만 돼도 넘친다. 값 제약을 모르니 확정은
못 하지만, 누적합 문제는 **합을 담는 변수는 `long`** 으로 두는 게 비용 0 인 습관이다. 위 수정안은 그렇게 했다.

#### 3. (사소) `n < 2K` 이면 `Integer.MIN_VALUE` 가 찍힌다

쌍이 하나도 없을 때 `maxSum` 초기값이 그대로 출력된다. 문제가 `2K ≤ N` 을 보장하면 무관하다.
보장이 없다면 그 경우 답이 뭔지(0? 불가능 표기?) 지문에서 확인해야 한다.

### 복잡도

- 시간: `O(N·K + N²)` — 쌍 열거가 지배적. 수정안은 `O(N)`
- 공간: `O(N)`

### 요약

겹치지 않는 조건을 `j = i+K` 로 옮긴 것과 두 단계 구조는 맞고, 무작위 대조에서 전부 정답이다.
문제는 규모다 — 쌍을 전부 도는 대신 **접미사 최댓값 배열 하나**를 두면 O(N) 이고 코드도 더 짧다.
"두 구간 중 하나를 고정하면 나머지는 범위 최댓값 질의" 라는 틀은 이 유형에서 계속 나오니 익혀 두면 좋다.
