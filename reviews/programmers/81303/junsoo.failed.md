# 표 편집 (실패 버전) (programmers/81303) — junsoo

`김준수/week3/표 편집.java`(정답, 링크드 리스트 버전)의 시행착오 주석에 나온 "java.util 클래스를
쓰니 시간초과 발생함"이 바로 이 버전이다. `Chart` 클래스가 `names`를 `ArrayList<Integer>`로 관리하고,
행 위치(`curr`)는 이 리스트 안의 인덱스로 취급한다.

## 무엇이 정답 버전과 다른가

- 정답 버전은 배열 두 개로 만든 더블 링크드 리스트라 삭제/복구가 각각 `O(1)`이다.
- 이 버전은 `names.remove(curr)`(삭제)와 `names.add(item[0], item[1])`(복구)를 쓰는데, 둘 다
  `ArrayList`에서 해당 인덱스 뒤의 모든 원소를 한 칸씩 밀거나 당기는 **`O(N)`** 연산이다.
- 최종 결과를 만들 때도 `chart.names.contains(i)`를 `N`번 반복 호출하는데(69~76행), `contains`
  자체가 `O(N)` 선형 탐색이라 이 부분만으로 **`O(N^2)`**이다.

## 검증: 로직 자체는 맞다 (반례 없음)

먼저 이게 "틀린 로직" 문제인지 "느린데 로직은 맞는" 문제인지 확인이 필요했다. `curr` 위치를
`U`/`D`로 직접 가감하고, `recover()`에서 `curr >= item[0]`이면 `curr++`로 보정하는 부분이
링크드 리스트 버전과 동일한 결과를 내는지 직접 대조했다.

- 정답 버전(`표 편집.java`)과 이 버전을 **같은 테스트 러너에 나란히 넣고**, 유효한 명령만 생성하는
  랜덤 시뮬레이터로 `N`을 2~41, 명령 수를 5~65개 범위에서 20,000건 무작위 대조했다.
  **불일치 0건.** (`N`을 3~10, 명령 5~15개로 좁힌 1차 시도에서도 20,000건 전부 일치했다.)
- 즉 위치 기반(`curr`를 인덱스로 보정)으로 다시 짠 아이디어 자체는 정답 버전과 동일한 결과를
  낸다 — **로직 버그가 아니라 순수하게 시간초과로 떨어지는 코드**로 판단된다.
  (검증에 쓴 임시 비교 코드는 커밋하지 않았다.)

## 실측: 실제로 시간이 얼마나 걸리는지

이 문제의 제약(`N <= 1,000,000`, `cmd 개수 <= 200,000`, 공식 확인)에 맞춰 직접 돌려봤다.

- `N=1,000,000`에 삭제 위주 명령 20만 개를 실행했을 때, **`C`/`Z`/`U`/`D` 처리(최종 결과 조합
  전)만으로 3.77초**가 걸렸다. Programmers 시간제한(보통 언어별 가중치를 줘도 수 초 이내)을
  넘길 가능성이 높다.
- 마지막 `contains()` 기반 결과 조합은 이보다 훨씬 심각하다. `N=20,000/40,000/80,000`으로
  스케일만 따로 재봤더니 `66ms → 236ms → 1,242ms`로 거의 정확히 `N^2`로 늘어났다. 이 비율로
  `N=1,000,000`까지 외삽하면 **최종 조합 한 단계에만 대략 3분 이상**이 걸린다는 계산이 나온다.
  실제로 `N=1,000,000`에서 끝까지 돌려서 확인하지는 않았다(현실적인 시간 안에 끝나지 않을 게
  분명해서 스케일 측정으로 대체함) — **완전한 실측은 아니고 추정**이라는 점은 밝혀둔다.

## 개선점

### 1. (치명) 삭제/복구를 `ArrayList`의 인덱스 삽입·삭제로 구현해 `O(N)`이 걸린다 — `collection-choice`

```java
names.remove(curr);              // O(N)
names.add(item[0], item[1]);     // O(N)
```

정답 버전처럼 배열 두 개로 만든 더블 링크드 리스트(또는 `LinkedList` + 노드 참조 직접 보관)를
쓰면 각각 `O(1)`이 된다.

### 2. (치명) 결과를 만들 때 `List.contains`를 `N`번 반복한다 — `time-complexity`

```java
for(int i = 0; i < n; i++){
    if(chart.names.contains(i)){ ... }   // O(N)을 N번 = O(N^2)
```

정답 버전은 "삭제된 인덱스만" 스택에 담아뒀다가 그 인덱스들만 `X`로 표시하므로 `O(N)`으로 끝난다.
이 방식으로 바꾸는 것만으로도 이 부분의 시간이 극적으로 줄어든다.

## 복잡도

- 시간: 이론상 `O(N·Σcmd)`(삭제/복구 각 `O(N)`) + 결과 조합 `O(N^2)`. 실측·외삽 모두 이 문제의
  상한(`N<=1,000,000`)에서 시간 제한을 넘길 것으로 보인다.
- 공간: `O(N)` — `names`, `stack`.

## 요약

`curr`를 리스트 인덱스로 보정하는 아이디어 자체는 정답 버전과 20,000건 무작위 대조에서 전부
일치했을 만큼 정확하다. 실패 원인은 논리가 아니라 `ArrayList`의 인덱스 삽입/삭제와 `contains`
선형 탐색이 만드는 시간초과다 — 정답 버전이 왜 굳이 배열 두 개로 링크드 리스트를 직접 구현했는지
정확히 보여주는 대조군이다.
