# 보석 쇼핑 (programmers/67258) — junsoo (실패)

## 접근

윈도우 길이를 1부터 N까지 늘려가며, 각 길이마다 왼쪽에서 오른쪽으로 슬라이딩하면서 그 길이의 윈도우 중 조건(모든 보석 포함)을 만족하는 게 있는지 찾는 방식이다. 대표 풀이(`junsoo.md`)의 투 포인터와 달리 길이를 고정하고 완전탐색에 가깝게 접근했다.

## 개선점

### 1. (치명) 윈도우를 슬라이드한 직후의 상태를 검사하지 않음 — off-by-one

안쪽 `for (int i = len; i < gems.length; i++)` 루프에서 조건 검사가 루프 **맨 앞**에서 일어나는데, 이 시점의 `window` 는 아직 이번 반복에서 슬라이드하기 **전** 상태다. 슬라이드(제거+추가)는 검사 이후, 루프 몸통 끝에서 일어난다. 그 결과 `i` 가 마지막 값(`gems.length - 1`)일 때 슬라이드해서 만들어진 **최종 윈도우는 그 어떤 반복에서도 검사되지 않는다** — 검사할 다음 반복이 없기 때문이다.

**실제로 돌려본 반례**: `gems = ["C","C","C","C","A","D"]`
- 기대 출력: `[4, 6]` (인덱스 3~5, `["C","A","D"]`)
- 실제 출력: `[1, 6]`

`len=3`일 때 인덱스 `(3,4,5)` 윈도우(`{C,A,D}`, 조건 만족)가 슬라이드 직후 상태라 검사를 못 받고 넘어가고, `len=4`, `len=5`도 같은 이유로 전부 놓친 뒤, `len=6`(전체 배열)에서야 초기 검사 단계에서 걸려 `[1, 6]` 을 반환한다.

무작위 2만 건(길이 1~15, 알파벳 5종) 대조에서 **3,155건(15.8%) 불일치** — 브루트포스 대비.

```java
// 수정 방향: 슬라이드 이후 상태도 검사하도록, 슬라이드를 검사 앞으로 옮기거나
// 루프 종료 후 마지막 윈도우를 한 번 더 검사해야 한다.
```

### 2. (중요) 길이를 1부터 순차 증가시키는 접근 자체가 O(N^2) — time-complexity

파일 상단 주석에 본인이 이미 "시간 초과 발생"이라고 적어뒀다. 각 길이마다 O(N) 슬라이딩을 다시 돌리므로 전체 O(N^2)이며, 대표 풀이의 투 포인터 O(N)로 대체된 이유가 이거다.

## 복잡도

- 시간: `O(N^2)` — 길이 루프 × 그 안의 슬라이딩 루프.
- 공간: `O(K)` — 해시맵 크기.

## 요약

접근 방향(길이를 늘려가며 탐색)은 이해할 수 있지만 검사와 슬라이드 순서가 어긋나 마지막 윈도우를 놓치는 off-by-one이 있고, 이와 별개로 시간복잡도도 제약을 못 맞춘다. 대표 풀이의 투 포인터 방식이 두 문제를 모두 해결한다.
