# 징검다리 건너기 (programmers/64062) — seongil (실패 버전)

## 접근

주석에 접근이 정확히 적혀 있습니다.

```
k 사이즈의 슬라이딩 윈도우를 활용하여 0번부터 length - k인덱스 까지
윈도우의 최댓값들 중 가장 작은 값이 뛸 수 있는 maximum 인원이다.
```

**이 문장이 이 문제의 정답입니다.** 대표 풀이(`징검다리건너기.java`)가 같은 관찰을 덱으로 `O(N)` 에 구현한 것이고, 이 파일은 같은 관찰을 창마다 직접 훑어서 구현한 것입니다.

그리고 여기에 최적화가 하나 들어가 있습니다 — `windowMax` 가 최댓값의 **인덱스**를 같이 돌려주고, 바깥에서 `i = val[0]` 로 점프합니다.

**중요한 결과부터 적습니다. 이 코드는 답이 틀리지 않습니다.**

무작위 30,000건(n=1~12, k=1~n, 값이 겹치는 입력 포함)을 브루트포스와 대조한 결과 **불일치 0건**이었습니다. 파일 이름이 `실패` 라서 오답을 예상했는데 아니었습니다. 실패 원인은 **시간초과**입니다.

### 점프 최적화는 왜 맞는가

창 `[i, i+k-1]` 의 최댓값이 인덱스 `m` 에 있다고 하면, `i < j <= m` 인 모든 창 `[j, j+k-1]` 은 `m` 을 포함합니다(`j <= m <= j+k-1`). 따라서 그 창들의 최댓값은 `stones[m]` 이상입니다. 우리가 구하는 건 창 최댓값들의 **최솟값**이고 이미 `stones[m]` 을 후보로 넣었으므로, 건너뛴 창들은 답을 더 낮출 수 없습니다. 그래서 `i = m` 으로 점프해도 안전합니다.

읽어서는 위험해 보이는 코드인데 실제로는 논리가 맞습니다. 짚어둘 만합니다.

## 개선점

### 1. (중요) 점프가 최악에서 한 칸씩만 나아가 `O(N·k)` 가 된다 — time-complexity

최댓값이 항상 창 맨 앞에 오는 입력, 즉 **내림차순 배열**이면 `val[0] == i` 라 점프가 아무것도 못 줄이고 `i++` 로 한 칸씩만 갑니다. 창마다 `windowMax` 가 `O(k)` 이므로 전체가 `O(N·k)` 입니다. `N = k = 2×10^5` 면 `4×10^10` 입니다.

실측했습니다. `n = 200,000`, `k = 100,000`.

| 입력 | 이 코드 | 대표 풀이(덱) | 대안 풀이(이분탐색) |
|---|---|---|---|
| **내림차순** | **1,671 ms** | 15 ms | 11 ms |
| 무작위 | 0 ms | 9 ms | 6 ms |

무작위 입력에서는 0 ms 로 끝납니다 — 점프가 잘 먹기 때문입니다. **입력 모양에 따라 성능이 1,671배 갈립니다.** 효율성 테스트가 내림차순에 가까운 케이스를 넣으면 그대로 시간초과입니다.

"평균은 빠른데 최악이 무너진다" 는 게 이 코드의 정확한 상태이고, 정확성 테스트는 통과하는데 효율성만 떨어지는 전형적인 모양입니다.

### 2. 고치는 법 — 이미 본인이 답을 갖고 있다

같은 관찰(`창 최댓값들의 최솟값`)을 유지한 채 창 최댓값 계산만 덱으로 바꾸면 `O(N)` 이 됩니다. 그게 대표 풀이 `이성일/week4/징검다리건너기.java` 입니다. 이 파일에서 대표 풀이로 넘어간 과정이 이 문제의 핵심 학습이라, **두 파일을 나란히 두는 게 맞습니다.** 지우지 마세요.

굳이 이 파일을 살린다면 `windowMax` 를 지우고 덱 한 벌로 대체하는 것이고, 그건 대표 풀이와 같아집니다.

### 3. (사소) `int[] {인덱스, 값}` 반환은 의도가 안 드러난다

`val[0]` 이 인덱스, `val[1]` 이 값이라는 걸 호출부를 봐야 압니다. 대표 풀이처럼 인덱스만 다루고 값은 `stones[idx]` 로 꺼내면 배열 반환이 필요 없어집니다.

### 4. 잘한 점 — `windowMax` 분리

창 최댓값 계산을 별도 메서드로 뺀 덕분에 **바깥 루프가 "창을 훑으며 최솟값 갱신" 이라는 뼈대만 남았습니다.** 그래서 위 1번 같은 복잡도 분석이 쉬웠습니다. 성능 때문에 버리는 코드지만 구조는 좋았습니다.
