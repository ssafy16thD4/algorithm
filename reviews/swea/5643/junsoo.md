# 키 순서 (swea/5643) — junsoo

## 접근

정방향/역방향 두 그래프를 만들어 각 사람마다 도달 가능한 노드 수(= 관계가 확정된 사람 수)를 DFS로
세고, `N - 1`과 같으면 순위를 알 수 있다고 판정한다. 상단 주석에 "큰 사람 수 + 작은 사람 수 == N-1"
이라는 판정 기준을 먼저 적어둔 게 코드를 읽기 전에 의도를 파악하는 데 도움이 된다.

## 개선점

### 1. (사소) `bigGraph`/`findBigCnt` 가 실제로는 "작은 사람"을 센다 — 이름과 실제 내용이 반대다 — `naming`

```java
bigGraph.get(u).add(v);      // 27행: u -> v 로 저장
smallGraph.get(v).add(u);    // 28행: v -> u 로 저장
```

입력 관계 `u v`가 "u가 v보다 크다"는 뜻이라면(이 문제의 일반적인 입력 형식), `bigGraph.get(u)`에
`v`를 넣는 것은 **u 기준으로 자신보다 작은 사람(v)을 저장하는 것**이다. 그런데 46행 주석은
`findBigCnt(i)`를 "자기보다 큰 사람 수 찾기"라고 적었고, `i`에서 `bigGraph`를 정방향으로 타고 가는
건 `i`가 더 크다고 명시된 쪽, 즉 **i보다 작은 사람들**을 찾는 것이다. `findSmallCnt`/`smallGraph`도
마찬가지로 뒤바뀌어 있다 — 실제로는 "자기보다 큰 사람"을 센다.

**다만 최종 결과에는 영향이 없다.** 50행에서 `cnt = findBigCnt(i) + findSmallCnt(i)`로 **합만** 보기
때문에, 두 함수가 세는 대상이 서로 바뀌어 있어도 "확정된 상대 수의 총합"이라는 값 자체는 동일하게
나온다. 직접 확인한 예시:

```
N=3, 관계: 1 2 / 2 3   →  출력 3 (전원이 자기 순위를 앎, 1>2>3 이 전이적으로 확정됨)
N=4, 관계: 1 2 / 3 4   →  출력 0 (그룹 간 비교 정보가 없어 아무도 확정 못함)
```

두 경우 모두 기대한 결과와 일치했다. 그래도 함수/변수 이름과 주석이 실제 동작과 반대로 적혀 있으면
나중에 이 코드를 고치거나 참고할 때 잘못 이해하기 쉬우니, `bigGraph`↔`smallGraph`,
`findBigCnt`↔`findSmallCnt`의 이름을 서로 바꾸거나 주석을 정정하는 게 좋다.

> 참고: 두 DFS(`findBigCnt`, `findSmallCnt`)가 `visited` 배열을 초기화 없이 이어서 공유하는데(44~54행),
> 이게 안전한 이유는 "i보다 큰 사람 집합"과 "i보다 작은 사람 집합"이 (모순 없는 전순서라는 문제 전제 하에)
> 항상 서로소이기 때문이다. 이 전제가 코드에 주석으로 남아 있지 않아서, 두 함수를 따로 떼어 재사용하면
> 위험할 수 있다는 점만 짚어둔다 — 이 파일 안에서는 문제 되지 않는다.

## 복잡도

- 시간: `O(N(N+M))` — 사람마다 그래프 전체를 DFS. `N`이 이 정도 크기에서 흔히 쓰이는 SWEA 문제(수백
  이내)라면 문제 되지 않는다.
- 공간: `O(N+M)` — 인접 리스트 두 개.

## 요약

판정 로직과 전이적 도달 가능성 계산은 맞고, 직접 만든 두 케이스에서도 기대한 답이 나왔다.
`bigGraph`/`smallGraph`와 두 카운트 함수의 이름이 실제로 세는 대상과 반대로 붙어 있는 게 유일한
흠인데, 다행히 최종 판정은 두 결과의 합만 쓰기 때문에 정답에는 영향이 없다.
