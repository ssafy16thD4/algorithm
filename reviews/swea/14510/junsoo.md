# 나무 높이 (swea/14510) — junsoo

## 접근

각 나무의 부족분(`diff = maxHeight - trees[i]`)을 그리디하게 "2" 위주로 채운 뒤(`oneCnt`, `twoCnt`),
`twoCnt - oneCnt >= 2`인 동안 2 하나를 1 두 개로 바꿔가며 균형을 맞추고, 마지막에 `oneCnt`/`twoCnt`의
대소 관계로 답을 구한다.

이 리뷰는 `data/problems.json`에 이 문제의 URL이 등록돼 있지 않아(`url: null`) 공식 지문을 확인하지
못했다. 코드와 상단 주석(특히 "1과 2의 개수 차가 최소가 될 때까지 2 하나를 1 두 개로 바꾼다", "1212...121로
끝난다")만으로 규칙을 역추적했고, 웹 검색으로 찾은 블로그 글도 정확한 규칙을 명시하지 않아 참고가 되지
못했다. 대신 아래처럼 코드를 실제로 컴파일·실행해 검증했다.

- 주석에 적힌 반례 `10 9 9 9` → 기대 답 `5`를 실제로 돌려서 확인: **출력 `5`, 일치.**
- 코드의 스왑 로직이 실제로 값을 바꾸는지 확인하려고 `10 0`(트리 2그루, 한쪽만 10 부족) 을 넣어봤다.
  스왑 전 그리디만 쓰면 `twoCnt=5, oneCnt=0` → 공식대로면 `10`이 나와야 하는데, 실제 실행 결과는 `7`이었다.
  손으로 스왑을 추적해도 `oneCnt=4, twoCnt=3` → `oneCnt*2-1=7`로 정확히 일치했다.

이 두 번째 케이스로 스왑 로직이 실제로 동작하며, "이미 사용한 2를 1 두 개로 바꿔서 더 이득을 보는" 방향의
교환 논증이 정확히 스왑 종료 조건(`차이 < 2`)에서 최솟값을 이룬다는 것도 손으로 확인했다 — `diff`가 고정된
한 그루 안에서는 `a_i(1의 개수)`가 이미 0/1로 최소인 상태에서 시작하므로 반대 방향(1 두 개 → 2 하나) 교환은
애초에 불가능하고, 코드가 시도하는 한 방향 스왑만으로 지역 최적 = 전역 최적이 된다. 다만 이건 **내가 재구성한
문제 규칙을 전제로 한 확인**이라, 공식 지문 기준으로 100% 같다고 단정하지는 못한다.

## 개선점

### 1. (사소) 균형 맞추기 `while` 루프는 닫힌 식으로도 대체 가능 — `time-complexity`

```java
while (twoCnt - oneCnt >= 2) {
    twoCnt--;
    oneCnt += 2;
}
```

한 번 반복에 `twoCnt-oneCnt` 차이가 3씩 줄어들기 때문에 반복 횟수가 초기 `twoCnt`(즉 `sum(diff_i)/2`
규모)에 비례한다. `N`과 나무 높이가 SWEA 기준으로 크지 않아 실제 시간 초과 위험은 없어 보이지만(정확한
상한은 지문을 확인 못 해 모름), `oneCnt + 2*twoCnt`(전체 합, 스왑에 불변)를 이용해 균형점을
`(합+2)/3` 근방으로 한 번에 계산하면 반복문 없이 O(1)로 끝낼 수 있다. 지금 상태로도 정답이라
급하게 고칠 이유는 없다.

## 복잡도

- 시간: `O(N + D)` — 입력을 훑는 `O(N)`에, 균형 맞추기 루프가 전체 부족분 합 `D = Σdiff_i`에 비례해서
  최악 `O(D)`. `D`의 상한을 지문에서 확인하지 못해 실제 문제 되는지는 판단 보류.
- 공간: `O(N)` — `trees` 배열 하나.
