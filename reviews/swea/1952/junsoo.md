# 수영장 (swea/1952) — junsoo

## 접근

먼저 달마다 `1일권 × 이용일수` 와 `1달권` 중 싼 쪽을 골라 `moneyPlan` 을 만들고, 그 위에서 3개월권으로 묶을 구간을 **그리디로** 정한다. 앞에서부터 훑은 결과(`frontSum`)와 뒤에서부터 훑은 결과(`backSum`) 중 작은 쪽을 취한 뒤, 마지막에 1년권과 비교한다.

주석의 시행착오 기록이 좋다. `5 3 3 6` 에 3개월권 10인 반례를 직접 찾아내서 "앞에서만 훑으면 안 된다"는 걸 확인하고 역방향 스캔을 추가한 흐름이 그대로 남아 있다. **문제를 발견한 방식 자체는 정확했다.** 다만 처방이 부족했다.

## 개선점

### 1. (치명) 앞/뒤 두 방향 그리디로는 최적해를 놓친다 — `wrong-algorithm`

역방향 스캔을 더한 것은 반례 하나를 막았을 뿐이고, 3개월권을 **어디서 끊을지**는 여전히 두 가지 순서만 본다. 최적 구간 분할이 "앞에서부터"도 "뒤에서부터"도 아닌 경우가 남는다.

**실제로 돌려본 반례** (안찬웅 완전탐색 코드와 무작위 대조 중 발견, 별도 DP로 재확인):

```
1
10 49 62 456
17 0 18 1 3 11 20 9 10 9 0 18
```

- 이 코드 출력: `#1 248`
- 정답: `#1 245`

최적 조합은 `1~3월 3개월권(62) → 4월 1일권(10) → 5~7월 3개월권(62) → 8~10월 3개월권(62) → 11월 1일권(0) → 12월 1달권(49)` = **245** 다. 3개월권 구간이 `1-3, 5-7, 8-10` 으로 **중간에 한 달을 건너뛰고** 끊기는데, 앞/뒤 어느 방향의 단순 스캔으로도 이 분할은 나오지 않는다.

### 2. (치명) 그리디 판정에 쓴 부등호가 3개월권을 과소 선택한다 — `logic-edge-case`

```java
if(monthCost > month3) { frontSum += month3; start += 3; }
```

`monthCost == month3` 일 때 3개월권을 쓰지 않는다. 비용은 같으니 이 한 수만으로 손해는 아니지만, 3개월권을 쓰면 **경계가 3칸 밀려서 이후 분할이 통째로 달라진다.** 그리디에서 동점 처리는 뒤쪽 선택을 바꾸므로 안전하지 않다. (이 항목만 `>=` 로 고쳐도 위 반례는 여전히 틀린다 — 근본 원인은 1번이다.)

### 3. 고칠 방향 — 그리디를 버리고 DP로

달이 12개뿐이라 완전탐색·DP 어느 쪽이든 비용이 사실상 0이다. 그리디를 다듬을 이유가 없다.

```java
int[] dp = new int[15];              // dp[i] = i월부터 12월까지의 최소 비용
for (int i = 11; i >= 0; i--) {
    dp[i] = Math.min(day * plan[i] + dp[i + 1],   // 1일권
             Math.min(month + dp[i + 1],           // 1달권
                      month3 + dp[Math.min(i + 3, 12)])); // 3개월권
}
int result = Math.min(dp[0], year);
```

**검증**: 위 DP를 그대로 돌려 문제의 반례에서 `245` 를 확인했고, 안찬웅의 완전탐색 코드와도 값이 일치한다. `dp` 배열을 15로 잡은 것은 `i+3` 이 최대 14까지 가기 때문이다(`Math.min` 을 쓰면 13이면 충분하다).

## 복잡도

- 시간: `O(12)` — 상수. 속도는 문제가 아니었다.
- 공간: `O(12)` — `plan`, `moneyPlan`.

## 요약

1일권↔1달권을 먼저 정리해 문제를 12칸 배열로 줄인 것까지는 좋은 정리다. 하지만 그 뒤 3개월권 구간을 그리디로 끊는 순간 최적성이 깨진다 — 앞/뒤 양방향 스캔은 본인이 찾은 반례 하나를 막았을 뿐 일반해가 아니다. 12개월짜리 DP면 세 줄로 끝나고 반례도 사라진다.
