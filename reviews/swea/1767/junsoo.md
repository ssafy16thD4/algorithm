# 프로세서 연결하기 (swea/1767) — junsoo

## 접근

각 코어마다 상하좌우 4방향 연결 시도 + "연결 안 함" 1가지를 더해 5갈래로 백트래킹한다.
전원 연결된 코어 수를 최우선으로, 같으면 전선 수가 적은 쪽으로 갱신하는 종료 조건이 문제 규칙과
정확히 일치한다. `canConnect`/`connect`/`unconnect`로 역할을 나눠서 백트래킹 본문이 짧고 읽기 쉽다.
파일 상단에 시행착오(상하좌우만 돌다 "연결 안 함" 선택지가 빠졌던 것, 가장자리 코어 최적화)를 남긴 것도 좋다.

## 개선점

### 1. (중요) 가장자리 코어 제외 조건이 `&&`라서 사실상 항상 거짓 — `dead-code`

```java
if(i == 0 && i == N - 1 && j == 0 && j == N - 1) continue;
```

주석(59~60행)의 의도는 "가장자리 코어는 `cores` 목록에서 아예 뺀다"인데, 네 조건을 전부 `&&`로 묶어서
`i==0`이면서 동시에 `i==N-1`이어야 하므로(`N==1`이 아닌 한 불가능) **이 `continue`는 사실상 실행되지
않는다.** 가장자리 코어도 전부 `cores`에 들어간다. 의도대로 하려면:

```java
if(i == 0 || i == N - 1 || j == 0 || j == N - 1) continue;
```

**다만 최종 출력에는 영향이 없다.** `backtrack` 144행에 동일한 가장자리 판정이 `||`로 한 번 더 있고,
가장자리 코어를 만나면 배선 시도 없이 `completeCnt + 1`만 하고 바로 다음 코어로 넘어가기 때문에, 목록에
남아 있어도 배선 탐색(`canConnect`/`connect`)에는 참여하지 않는다. 모든 분기에 가장자리 코어 수만큼
`completeCnt`가 똑같이 더해지므로 "어느 배치가 더 나은가"를 비교하는 상대적 결과(`result`)는 동일하다.

- 직접 확인: `SWEA1767.java`를 그대로 컴파일해 5×5 반례(가장자리 4개 + 내부 코어들 섞인 보드)를 돌린
  결과와, `&&`를 `||`로 고친 임시 사본을 같은 입력으로 돌린 결과를 비교했다 — **둘 다 `6`으로 동일.**
  (검증에 쓴 파일은 커밋하지 않음.)

그래도 주석에 적은 "가장자리 코어를 배열에서 빼서 수행 시간을 줄였다"는 최적화가 실제로는 전혀 적용되지
않고 있다는 뜻이므로, 의도대로 고쳐서 144행의 검사를 실질적인 이득으로 만드는 편이 좋다.

### 2. (사소) `canConnect` 안의 지역변수 `result`가 정적 필드 `result`를 가린다 — `naming`

```java
static int result;           // 35행, 최소 전선 수 (전역)
...
private static boolean canConnect(...) {
    boolean result = true;   // 77행, 지역 변수 — 타입도 다르고 의미도 다름
```

스코프상 버그는 아니지만 같은 이름이 타입도 의미도 다르게 재사용돼 읽을 때 헷갈린다. `connectable` 같은
이름으로 바꾸면 좋다.

  + "연결 안 함" 1가지로 분기한다. `N`과 코어 배치 제약상 실제로는 통과하는 걸 코드 상단 주석(`40,452kb
  284ms`)으로 확인했다 — 이 수치는 SWEA 채점 결과를 그대로 옮겨 적은 것으로 보이며, 내가 다시 채점해
  검증한 것은 아니다.
