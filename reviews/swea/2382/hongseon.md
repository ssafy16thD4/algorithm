## 접근

이 문제에서 제일 까다로운 조건은 "한 칸에 여러 군집이 모이면 **가장 큰 군집의 방향**을 따른다" 인데,
이 코드는 그걸 **정렬 순서 + 덮어쓰기**로 바꿨다.

```cpp
sort(v.begin(), v.end(), [](const Unit &a, const Unit &b) { return a.size < b.size; });   // 오름차순
...
else {   // 이미 누가 차지한 칸
    board_size[v[i].x][v[i].y] += v[i].size;
    board_dir[v[i].x][v[i].y] = v[i].dir;     // 나중에 온 놈이 항상 더 크다
}
```

작은 것부터 처리하므로 나중에 도착하는 군집이 항상 더 크고, 방향을 그냥 덮어쓰면 그게 곧 최대 군집의
방향이 된다. 크기 비교문이 하나도 없다. 3개 이상이 한 칸에 모이는 경우도 특별 케이스가 아니게 된다.

**격자를 임시 버퍼로 쓰고 매 초 비우는 구조도 좋다.** `board_size`/`board_dir` 에 모아 합친 다음
`used_loc` 에 적어둔 칸만 되짚어 `v` 를 다시 만들고 그 칸을 `-1` 로 되돌린다. 격자 전체를 매 초
`fill` 하지 않으므로 `N = 100` 이어도 초당 비용이 군집 수에 비례한다.

> 같은 문제를 푼 `김준수/week6/미생물 격리.java` 는 군집 쌍을 전부 비교해서 합체를 찾기 때문에
> 초당 `O(K²)` 다. `K, M ≤ 1000` 이면 최대 10⁹ 에 닿는다. 이 코드는 `O(K log K)` 로 한 차수 낮다.

## 개선점

### 1. (중요) 크기가 0이 된 군집이 사라지지 않는다 — <logic-edge-case>

```cpp
if (v[i].x == 0 || v[i].x == n - 1 || v[i].y == 0 || v[i].y == n - 1) {
    board_size[v[i].x][v[i].y] /= 2;
    board_dir[v[i].x][v[i].y] = change_dir[v[i].dir];
}
```

약품 처리로 `size` 가 0이 돼도 `used_loc` 에 이미 들어가 있어서, 다음 초에 **크기 0짜리 군집으로
다시 `v` 에 실린다.** 문제 조건상 미생물이 다 죽으면 그 군집은 없어져야 한다.

**합계에는 영향이 없다** (0을 더하니까). 방향 결정에도 영향이 없다 — 오름차순 정렬이라 0짜리는
항상 맨 앞에서 처리되고, 뒤에 오는 진짜 군집이 방향을 덮어쓴다. 그래서 **답이 틀리지는 않을 것으로 보인다.**

다만 이 군집들이 매 초 정렬·이동·격자 기록에 계속 참여한다. `M = 1000` 이면 죽은 군집이 계속 쌓여
`K` 가 줄지 않는다. 되짚는 루프에서 한 줄로 걸러진다.

```cpp
for (int i = 0; i < used_loc.size(); i++) {
    int x = used_loc[i].x, y = used_loc[i].y;
    if (board_size[x][y] > 0)                          // 다 죽은 군집은 버린다
        v.push_back({x, y, board_size[x][y], board_dir[x][y]});
    board_size[x][y] = -1;
    board_dir[x][y] = -1;
}
```

**확인 못 함** — g++ 가 없어 죽은 군집이 실제로 몇 개까지 쌓이는지, 답이 정말 안 바뀌는지
돌려보지 못했다. 위 판단은 코드를 읽은 결과다.

### 2. (중요) 합체가 먼저 일어난 칸에는 약품 처리가 다시 적용되지 않는다 — <logic-edge-case>

빈 칸에 처음 도착한 군집만 가장자리 검사를 받고, 그 뒤에 같은 칸으로 합쳐지는 군집은
`board_size += size` 만 하고 **절반이 죽는 처리를 받지 않는다.** 방향도 반전되지 않은 값으로 덮인다.

**실제로 도달하지 않는 경로로 보인다.** 가장자리 칸에 안쪽에서 들어올 수 있는 이웃은 한 칸뿐이고
(나머지 이웃은 전부 가장자리인데, 가장자리에 있던 군집은 직전 초에 반전돼 안쪽을 향한다),
초기 군집은 가장자리에 놓이지 않는다. 즉 **한 칸에 두 군집이 같은 초에 도착하는 가장자리 칸은 없다.**

그래도 이건 코드가 아니라 문제의 기하에서 나오는 보장이라, 읽는 사람이 매번 다시 증명해야 한다.
합체를 다 끝낸 뒤에 가장자리 처리를 한 번 하는 순서로 바꾸면 그 증명이 필요 없어진다 —
`used_loc` 를 되짚는 루프에서 처리하면 자연스럽다.

**확인 못 함** — 위 도달 불가 논증은 코드와 문제 조건을 읽고 세운 것이고, 실행으로 확인하지 않았다.

### 3. (사소) `// Unit &cur = v[i];` — <dead-code>

쓰다 만 참조 선언이 주석으로 남아 있다. 실제로 이 참조를 살리면 아래의
`v[i].x`, `v[i].y`, `v[i].size`, `v[i].dir` 반복이 전부 `cur.x` 로 짧아진다. 지우거나 살리거나 둘 중 하나다.

### 4. (사소) `cin` 가속 설정이 없다

`main` 에 `ios::sync_with_stdio(0); cin.tie(0);` 가 빠져 있다. `K ≤ 1000`, `T` 가 여러 개면
입력이 수천 줄이라 체감이 될 수 있다. 같은 주차의 `swea2112.cpp` 에는 들어가 있다.

### 5. (사소) `v.resize(k)` 는 이전 케이스의 값을 남긴다

`v.clear()` 없이 `resize(k)` 라 이전 케이스가 더 컸으면 앞쪽 원소가 남는다.
바로 아래 루프가 `k` 개를 전부 덮어쓰므로 **지금은 문제가 없지만**, 케이스 간 상태를 남기는 형태다.
`v.assign(k, Unit{})` 이나 `v.clear(); v.resize(k);` 가 뜻이 분명하다.

## 복잡도

- 시간: `O(T·M·K log K)` — 매 초 정렬이 지배적. 격자를 전부 훑지 않는 게 핵심
- 공간: `O(N² + K)` — `board_size`/`board_dir` 두 격자와 군집 목록

## 요약

크기 오름차순 정렬 + 방향 덮어쓰기로 "가장 큰 군집의 방향" 조건을 비교문 없이 처리하고,
격자를 임시 버퍼로만 써서 매 초 비용을 군집 수에 묶은 설계가 좋다. 같은 문제의 Java 풀이보다
한 차수 빠르다. 손봐야 할 건 죽은 군집(크기 0)이 목록에서 안 빠져 계속 실린다는 점이고,
가장자리 처리와 합체의 순서는 지금 기하 조건 덕에 안전하지만 순서를 바꿔두면 그 증명이 필요 없어진다.
