# 탈주범 검거 (swea/1953) — junsoo

## 접근

터널 타입별 이동 가능 방향을 `dx[8][4]` / `dy[8][4]` 테이블로 정리하고, BFS로 시간 `L` 까지 도달 가능한 칸을 센다. `dist` 를 1부터 시작해 `dist == L` 이면 더 뻗지 않는 처리로 "L 시간 이내"를 깔끔하게 표현했다.

**가장 좋은 판단은 `isConnect` 를 분리한 것이다.** 주석의 시행착오가 정확하다 — 현재 칸에서 옆 칸으로 나갈 수 있다는 것만으로는 부족하고, **옆 칸도 이쪽을 향해 열려 있어야** 한다. `+` 옆에 `|` 가 가로로 붙어 있으면 `+` 는 오른쪽으로 나갈 수 있지만 `|` 는 좌우가 막혀 있어서 실제로는 못 간다. 이걸 양방향으로 검사한다:

```java
if(nx1 == x2 && ny1 == y2) canGo1 = true;   // 현재 칸 -> 옆 칸
if(nx2 == x1 && ny2 == y1) canGo2 = true;   // 옆 칸 -> 현재 칸
return (canGo1 && canGo2);
```

파이프 연결 문제에서 가장 자주 틀리는 지점을 정확히 짚었다.

방향 테이블도 검산해봤는데 7종류가 전부 문제 정의와 맞는다 — 1번 십자(상하좌우), 2번 수직(상하), 3번 수평(좌우), 4번 상+우, 5번 하+우, 6번 하+좌, 7번 상+좌.

## 개선점

### 1. (사소) `dx`/`dy` 의 빈 자리를 `0` 으로 채운 방식이 우연히 맞아떨어진다 — `magic-number`

타입 4를 보면 이렇다:

```java
dx[4] = {-1, 0, 0, 0};
dy[4] = { 0, 0, 0, 1};
```

`i=0` 에서 `(-1, 0)` = 위, `i=3` 에서 `(0, +1)` = 오른쪽. **두 방향이 서로 다른 인덱스에 들어 있어서** 동작한다. `i=1, 2` 는 `(0,0)` 이라 자기 자신을 가리키는데, BFS 쪽에서 `dist[nx][ny] != 0` 에 걸려 조용히 걸러진다.

답은 맞지만 위험한 구조다. 만약 두 방향이 같은 인덱스에 겹쳤다면 한 방향이 사라졌을 것이고, `(0,0)` 이 걸러지는 것도 "이미 방문한 칸"이라는 **다른 이유** 덕분이라 우연에 기대고 있다. `isConnect` 에서도 같은 `(0,0)` 이 돌아가는데, 여기서는 `nx1 == x2` 비교라 자기 자신과 옆 칸이 같을 수 없어 문제가 안 될 뿐이다.

방향 집합을 가변 길이로 두면 의도가 그대로 드러난다:

```java
// 타입별 이동 가능 방향만 담는다. 0: 상, 1: 하, 2: 좌, 3: 우
static final int[][] MOVES = {
    {},                  // 0: 터널 없음
    {0, 1, 2, 3},        // 1: 십자
    {0, 1},              // 2: 수직
    {2, 3},              // 3: 수평
    {0, 3},              // 4: 상우
    {1, 3},              // 5: 하우
    {1, 2},              // 6: 하좌
    {0, 2},              // 7: 상좌
};
static final int[] DX = {-1, 1, 0, 0};
static final int[] DY = { 0, 0, -1, 1};
```

`for (int d : MOVES[pipeType])` 로 돌면 빈 자리를 채울 일이 없어진다.

## 복잡도

- 시간: `O(N × M)` — 각 칸을 한 번씩 방문. `isConnect` 가 칸마다 상수 4회 도는 것이 곱해진다.
- 공간: `O(N × M)` — `board` + `dist` + 큐.

## 요약

파이프 문제의 핵심인 **양방향 연결 검사**를 별도 함수로 분리해 정확히 처리했고, 방향 테이블 7종도 전부 맞다. `dist == L` 로 시간 제한을 표현한 것도 간결하다. 지적할 것은 방향 테이블의 `(0,0)` 패딩이 우연히 안전한 구조라는 점 하나인데, 가변 길이 배열로 바꾸면 의도가 코드에 드러난다.
