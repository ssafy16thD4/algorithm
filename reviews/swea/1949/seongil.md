# 등산로 조성 (swea/1949) — seongil

## 접근

"어느 칸을 얼마만큼 깎을 것인가"를 탐색 안에서 정하지 않고, **바깥에서 전부 나열**한다. 모든 칸 `(i,j)` × 모든 깎기 양 `v = 1..K` 를 순회하며 `map[i][j] -= v` 로 지형을 고정한 뒤, 그 지형 위에서 순수한 내리막 DFS를 돌린다.

탐색 자체는 깎기를 전혀 몰라도 되는 단순한 형태가 되고(`map[nx][ny] >= map[x][y] continue` 한 줄), 상태 관리가 `visited` 백트래킹 하나로 끝난다. **"경우의 수를 바깥으로 빼서 안쪽을 단순하게 만든다"** 는 판단은 시뮬레이션 문제에서 꽤 자주 통하는 정리법이고, 여기서도 읽기 쉬운 코드로 이어졌다.

`map[i][j] -= v` 후 `map[i][j] += v` 로 정확히 되돌리는 것도 빠짐없이 되어 있다.

**검증**: 김준수·안찬웅의 통과 코드와 무작위 입력 60건(N=3~7, K=1~4)을 대조했고 **3개 구현이 전부 일치**했다.

## 개선점

### 1. (중요) 깎는 양을 `1..K` 전부 시도할 필요가 없다 — `redundant-loop`

```java
for (int v = 1; v <= k; v++) {
    map[i][j] -= v;
    ...
}
```

등산로는 **아래로만** 내려간다. 그래서 어떤 칸을 깎을 때, 지나갈 수만 있다면 **가장 적게 깎는 쪽이 항상 최소한 같거나 더 낫다** — 그 칸이 높게 남을수록 다음 칸으로 갈 조건이 느슨해지기 때문이다. 즉 `v` 를 1부터 K까지 도는 K배 반복이 통째로 불필요하다.

김준수 코드는 이 성질을 써서 깎은 뒤 높이를 `이전칸 - 1` **한 값으로 고정**했다. 같은 정리를 이 구조에 적용하면 `v` 루프가 사라져 전체가 K배 빨라진다. N ≤ 8, K ≤ 5라 지금은 통과하지만, 지적할 만한 가장 큰 낭비다.

### 2. (사소) 마지막 "공사 안할 때 dfs" 는 죽은 코드이면서 카운트도 하나 어긋나 있다 — `dead-code`, `off-by-one`

```java
// 공사 안할 때 dfs
for (int[] point : highPoints) {
    dfs(map, visited, point, 0);
}
```

위의 `v` 루프와 비교하면 두 군데가 다르다.

- 시작 `cnt` 가 `0` 이다. 위쪽은 `dfs(..., 1)` 로 시작한다. 등산로 길이는 **칸 수**라 시작 칸도 1로 세야 하므로, 이 호출은 항상 **1 작은 값**을 낸다.
- `visited[point] = true` 를 안 걸고 들어간다. (높이가 단조 감소라 시작점으로 되돌아올 수는 없어서 실제 오답으로 이어지지는 않는다.)

그런데 **이 루프는 있으나 마나다.** 경로에 포함되지 않는 칸을 깎는 경우가 위의 `v` 루프에 이미 들어 있어서, "아무 데도 안 깎은 지형"은 그 안에서 이미 다 탐색된다. 결국 항상 더 작은 값만 내놓는 죽은 코드다. 지우는 게 맞다.

### 3. (사소) `answer = 0;` 이 두 번 나온다 — `dead-code`

테스트케이스 루프 안에서 DFS 앞에 한 번, 출력 뒤에 한 번 초기화한다. 뒤쪽 하나는 다음 반복의 앞쪽 초기화에 덮여서 아무 일도 하지 않는다.

## 복잡도

- 시간: `O(N^2 × K × 봉우리수 × 4^(경로길이))` — 앞의 `N^2 × K` 가 "어디를 얼마나 깎나"를 나열하는 비용이고, 개선점 1을 적용하면 `K` 가 빠진다.
- 공간: `O(N^2)` — `map`, `visited`. 백트래킹이라 경로별 복사는 없다.

## 요약

깎기를 탐색 밖으로 빼서 안쪽 DFS를 아주 단순하게 만든 구성이 좋고, 답도 정확하다. 대신 그 대가로 `N^2 × K` 배의 나열을 하고 있는데, "지나갈 수 있는 선에서 가장 적게 깎는 게 항상 최적"이라는 성질을 쓰면 `K` 배는 바로 없앨 수 있다. 마지막 무공사 DFS 루프는 지워도 답이 변하지 않는다.
