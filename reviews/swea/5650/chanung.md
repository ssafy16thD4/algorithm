# 핀볼 게임 (swea/5650) — chanung

## 접근

빈 칸(0)마다 DFS로 공을 굴려 블랙홀에 빠지거나 출발점으로 돌아올 때까지 시뮬레이션하고, 그 경로에서 얻은 점수의 최댓값을 갱신하는 구조다. 각 상태(x, y, dir, score)를 넘기는 재귀 시그니처는 명확하고, 상단 주석에 알고리즘 단계를 미리 적어둔 점은 좋다. 다만 실제 구현이 그 주석 스펙과 여러 군데에서 어긋나 있다.

## 개선점

### 1. (치명) 디버그 출력이 그대로 남아 채점 출력에 섞인다 — `logic-edge-case`

`dfs` 첫 줄(66행)에 `System.out.println("x: " + x + " y: " + y + " dir: " + dir + " score: " + score);` 가 있다. DFS가 호출될 때마다 찍히므로, 기대 출력(`#1 3` 같은 한 줄)과 전혀 다른 수많은 줄이 표준출력에 섞여 나간다. 알고리즘이 전부 맞아도 이 줄 하나 때문에 100% 오답 처리된다. 제출 전 삭제해야 한다.

### 2. (치명) 웜홀 처리가 주석에 적힌 스펙대로 구현돼 있지 않다 — `wrong-algorithm`


파일 상단 주석(15행)은 "다음 칸이 웜홀일 경우 동일한 숫자를 가진 다른 웜홀로 나옴"이라고 되어 있는데, 실제 구현(150~154행)은:

```java
else if(6 <= graph[nx][ny] && graph[nx][ny] <= 10) {
    // 현재 웜홀에 있는 수와 같은 다른 웜홀수로 이동함
    return;
}
```

짝 웜홀 좌표를 찾아 이동하는 코드가 없고 그냥 `return`으로 끝낸다. 즉 웜홀에 들어가는 순간 그 시점까지의 점수로 게임이 종료돼 버려, 웜홀을 통과해서 더 많은 점수를 딸 수 있는 경로들이 전부 누락된다. 웜홀이 하나라도 있는 보드에서는 최댓값이 실제보다 작게 나올 수밖에 없다.

### 3. (치명) 4번 블록의 방향 분기 조건에 도달 불가능한 값이 섞여 있다 — `off-by-one`

1~3번 블록은 "돌아오는 두 방향"을 `dir` 값 두 개로 명시하고, 나머지 두 방향을 각각 처리하는 패턴이 일관되게 반복된다(우상=0,3 / 우하=0,1 / 좌하=1,2). 그런데 4번 블록(130~142행)만 패턴이 깨져 있다:

```java
else if(graph[nx][ny] == 4) {
    // dir이 좌상일 경우 돌아옴
    if(dir == 3 || dir == 4) {   // dir 은 0~3 범위라 dir==4 는 절대 참이 안 됨
        dir = (dir + 2) % 4;
    }
    else {
        if(dir == 0) dir = (dir + 3) % 4;
        if(dir == 1) dir = (dir + 1) % 4;
    }
}
```

주석대로라면 "좌상"이니 `dir == 2 || dir == 3` 이어야 하는데 `dir == 4`로 오타가 나 있다(`dx`/`dy` 배열 길이가 4라 dir은 0~3만 나온다). 그 결과 `dir == 2`(좌)로 4번 블록에 들어오면 첫 조건도 안 걸리고 else 분기의 `if(dir==0)`/`if(dir==1)`도 안 걸려서 `dir`이 전혀 바뀌지 않은 채 그대로 `dfs(nx, ny, dir, score+1)`로 넘어간다. 반사돼야 할 경로가 반사 없이 직진 취급되면서 점수만 잘못 올라간 상태로 시뮬레이션이 이어진다.

### 4. (치명) 발사 방향을 오른쪽(0) 하나만 시도한다 — `wrong-algorithm`

```java
if(graph[i][j] == 0) {
    startX = i; startY = j;
    dfs(i, j, 0, 0);
}
```

빈 칸마다 `dir=0`(우측)으로만 DFS를 한 번 호출한다. 이 문제는 공을 놓을 칸뿐 아니라 발사 방향(상하좌우 4방향)도 자유롭게 고를 수 있는 게 규칙이라, 같은 칸이라도 방향에 따라 전혀 다른(더 높은) 점수가 나올 수 있다. 지금 구조로는 `graph[i][j]==0`인 칸마다 4방향을 전부 시도해야 하는데 1방향만 보고 있어 최댓값을 과소평가한다.
※ 이 항목은 문제 페이지를 직접 열어 재확인한 건 아니고(리소스 없음 — `resolve.mjs`가 준 `url`이 비어 있음), SWEA 5650이 "칸+방향을 모두 탐색"하는 문제로 널리 알려진 규칙에 근거했다. 코드 자체만 보면 방향 인자 `dir`을 굳이 시그니처에 넘기면서도 시작 시점엔 상수 0 하나만 쓰는 점이 이 규칙과의 불일치를 뒷받침한다.

## 복잡도

- 시간: `O(N^4)` — 빈 칸 O(N^2)개마다 한 방향(원래는 4방향)으로 시뮬레이션하는데, 각 시뮬레이션은 분기 없이 상태가 결정론적으로 이어지므로 경로 길이는 최악 O(N^2). 웜홀·4방향이 정상적으로 붙어도 상수배만 늘어나는 수준.
- 공간: `O(N^2)` — 보드 저장 + 재귀 깊이가 경로 길이(≤ N^2)만큼.

## 요약

DFS로 상태를 결정론적으로 이어가는 뼈대 자체는 무리가 없지만, 디버그 출력 잔존·웜홀 미구현·4번 블록 방향 오타·시작 방향 고정까지 겹쳐서 지금 상태로는 거의 항상 오답이다. 특히 디버그 출력과 웜홀 `return`은 코드만 봐도 확정적인 버그이고, 나머지 둘도 자기 자신의 주석·시그니처와 실제 동작이 어긋나는 지점이라 확신도가 높다.
