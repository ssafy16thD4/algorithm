# 디저트 카페 (swea/2105) — hongseon

> `compiles: null` — 이 환경에 g++ 가 없어 **컴파일·실행을 하지 못했다.** 컴파일 실패라는 뜻이 아니라
> 판정을 못 했다는 뜻이다. 아래는 전부 코드를 읽고 쓴 것이고, 반례를 돌려본 것은 없다.

## 접근

사각 경로를 네 변의 길이로 짜맞추는 대신, **"마주보는 두 변의 길이가 같다" 는 제약 하나만 상태로 들고
나머지는 기하가 알아서 맞게** 만들었다.

```cpp
if (dir == 2) zero_cnt--;
...
if (dir == 2) { if (zero_cnt > 0) backtrack(nx, ny, dir, ...); else backtrack(nx, ny, dir + 1, ...); }
```

`zero_cnt` 는 0번 방향(우상)으로 몇 칸 갔는지를 세어 두었다가, 2번 방향(좌하)에서 정확히 그만큼만
가도록 강제한다. 그러면 3번 방향(좌상)의 길이는 **자동으로** 1번 방향과 같아지므로, 종료 조건이
`x == startx && y == starty && dir == 3` 한 줄로 끝난다. 네 변을 다 관리하지 않아도 되는 이유를
스스로 증명하고 짠 코드다.

시작점을 모든 칸에서 0번 방향으로만 출발시킨 것도 정확하다 — 마름모의 **가장 왼쪽 꼭짓점**은 유일하므로
같은 경로를 두 번 세지 않는다.

`bool used[101]` 로 디저트 중복을 관리한 것도 좋은 선택이다. 번호가 1~100 의 작은 정수라
`set` 이나 해시가 필요 없고, 백트래킹의 가장 안쪽에서 도는 검사라 상수배가 그대로 실행 시간에 실린다.
(같은 문제를 푼 `이성일/week6/SWEA2105.java` 는 여기서 `HashSet<Integer>` 를 써서 박싱 비용을 낸다.)

함수 맨 위에 "호출됐을 때 확정된 것들" 을 적어둔 주석 블록도 값어치가 있다. 백트래킹은 프레임 하나가
무엇을 보장하는지가 곧 정확성이라, 그 불변식을 글로 적어두면 나중에 읽을 때 검산이 된다.

## 개선점

### 1. (중요) 주석 처리된 디버그 출력 3덩이 — <dead-code>

`backtrack` 안에 `if (startx == 3 && starty == 0)` 로 시작하는 디버그 블록이 두 곳, 그 밖에도
`// cout << " " << board[nx][ny] ...` 가 남아 있다. **전부 특정 케이스(3,0)를 추적하려고 넣은 임시 코드**라
지금은 읽는 사람에게 "이 좌표가 특별한가?" 하는 잘못된 신호만 준다.

디버깅이 끝났으면 지우는 게 맞다. 다시 필요하면 git 이력에서 꺼내면 된다.
같은 문제가 `week5/breakthewall.cpp` 에서는 훨씬 심하다 — 그쪽은 203줄 중 60줄 가까이가 주석 처리된 코드다.

### 2. (사소) `zero_cnt` 는 이름이 값을 설명하지 못한다 — <naming>

이 변수가 실제로 담는 건 "0번 방향으로 이동한 칸 수" 이자 "2번 방향으로 더 가야 할 칸 수" 다.
`zero_cnt` 는 "0의 개수" 로도 읽혀서 주석 없이는 뜻이 안 잡힌다.

```cpp
int remain_side;   // 2번 방향으로 남은 이동 수 (= 0번 방향 변의 길이)
```

이 풀이에서 제일 영리한 부분인데 이름 때문에 그게 안 드러난다.

### 3. (사소) 시작 칸 복귀 시 `used` 를 되돌리지 않고 return 한다

```cpp
used[board[x][y]] = true;
...
if (x == startx && y == starty && dir == 3) { answer = max(answer, curcnt - 1); return; }
```

이 경로만 `used[...] = false` 없이 빠져나간다. **실제로는 문제가 없다** — 그 칸은 최초 호출에서 이미
`true` 로 잡혀 있었고 그 프레임이 끝날 때 되돌리기 때문이다. 다만 다른 return 지점 두 곳은 모두
직접 되돌리고 있어서, 여기만 규칙이 다른 이유를 읽는 사람이 한 번 더 확인해야 한다.
주석 한 줄이라도 붙여두면 좋다.

**확인 못 함** — g++ 가 없어 실제로 `used` 가 새는지 돌려보지는 못했다. 위 판단은 코드를 읽은 결과다.

## 복잡도

- 시간: `O(T·N⁴)` — 시작 꼭짓점 N² × 그 지점에서 가능한 사각 경로 수. N ≤ 20 이라 여유롭다
- 공간: `O(N)` — 재귀 깊이(경로 길이)와 `used[101]` 고정 배열

## 요약

"마주보는 변의 길이가 같다" 는 제약 하나만 상태로 들고 나머지는 기하에 맡긴 설계가 좋다.
그 덕에 종료 조건이 한 줄이고, `bool[101]` 로 중복 검사까지 상수 시간이라 안쪽 루프에 군더더기가 없다.
실제로 손볼 건 알고리즘이 아니라 정리다 — 특정 좌표를 추적하던 디버그 블록 세 덩이를 지우고,
`zero_cnt` 에 제 뜻을 담은 이름을 주면 이 풀이의 영리한 부분이 코드에 그대로 드러난다.
