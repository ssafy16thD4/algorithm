# 보호 필름 (swea/2112) — junsoo (실패 버전)

## 접근

통과 버전과 **답은 같고 속도만 다르다.** 무작위 입력 60건(D=3~7, W=2~4, K=2~4)을 두 버전에 넣어 대조했는데 출력이 전부 일치했다. 즉 이 파일은 오답이 아니라 **시간초과**다. 정답 로직을 세워둔 상태에서 탐색 구조만 비효율적이었던 케이스라, 무엇이 시간을 잡아먹는지 보기에 좋은 자료다.

## 개선점

### 1. (치명) `visited` 배열 방식이 같은 행 조합을 순서만 바꿔 반복 탐색한다 — `time-complexity`

```java
for(int i = 0; i < D; i++) {
    ...
    visited[i] = true;
    useMed(i, 0);  dfs(i, 1);
    useMed(i, 1);  dfs(i, 1);
    ...
}
```

`dfs` 가 매 깊이마다 **0부터 D까지 전부** 다시 돌기 때문에, 행 `{1, 3}` 을 고르는 경우가 `1→3` 과 `3→1` 두 번 탐색된다. 행을 `m`개 고르는 조합 하나가 `m!` 번 중복된다. 조합 문제를 순열로 푼 셈이다.

게다가 `visited[i] = false;` 가 **주석 처리되어 있어** 상태 복원도 되지 않는다(`// visited[i] = false;`). 결과적으로 `visited` 는 읽히지도 않고(`dfs` 안에서 참조하지 않는다) 복원되지도 않는 **죽은 상태**다.

통과 버전은 이 루프를 통째로 없애고 `dfs(row, count)` 가 **`row` 부터 앞으로만** 진행하게 바꿨다:

```java
dfs(row + 1, count);            // 이 행 안 씀
useMed(row, 0); ... dfs(row + 1, count + 1);   // A약
useMed(row, 1); ... dfs(row + 1, count + 1);   // B약
```

조합 하나가 정확히 한 번씩만 나온다.

**실측 차이** — D=13, W=20, K=7 무작위 입력 하나:

| 버전 | 출력 | 실행 시간 |
| --- | --- | --- |
| 통과 버전 | `#1 7` | **156ms** |
| 이 버전 | `#1 7` | **2510ms** |

같은 답에 **16배**다. 테스트케이스가 여러 개 붙으면 그대로 시간초과로 이어진다.

### 2. (중요) 리프에서만 판정해서 조기 확정 기회를 놓친다 — `redundant-loop`

이 버전은 재귀 끝에서 `isOK()` 를 확인하는 구조라, 약을 넣은 직후 이미 조건을 만족했더라도 더 깊이 들어간다. 통과 버전은 약을 넣자마자 검사해서 만족하면 그 자리에서 `result` 를 확정하고 재귀를 끊는다 — 약을 더 넣어봐야 개수만 늘기 때문이다. 1번을 고치더라도 이건 따로 챙겨야 하는 가지치기다.

### 3. (사소) 주석 처리된 `visited[i] = false;` — `dead-code`

위에서 짚은 그 줄이다. 복원을 하려다 만 흔적이 남아 있는데, 통과 버전에서는 `visited` 자체가 사라졌다.

## 복잡도

- 시간: 사실상 `O(D! × D × W)` 수준의 중복 탐색. 통과 버전은 `O(3^D × D × W)`.
- 공간: `O(D × W)` — 같다.

## 요약

**오답이 아니라 시간초과**이고, 원인이 한 곳으로 좁혀진다 — 조합을 골라야 하는데 매 깊이마다 전체 행을 다시 도는 순열 탐색을 했다. `row` 파라미터로 "앞으로만 진행"을 강제하는 것이 통과 버전과의 유일한 구조적 차이이고, 실측 2510ms → 156ms 로 갈린다. 본인이 통과 버전 주석에 이 시행착오를 정확히 기록해두었다.
