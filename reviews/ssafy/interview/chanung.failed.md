# 면접 (ssafy/interview) — chanung (실패 버전)
## 접근

n문제 중 m개를 맞췄을 때 총점이 **최소**가 되는 배치를 직접 구성하고, 그 배치를 문제 규칙대로
한 번 시뮬레이션한다. 관찰 세 개가 들어가 있고 셋 다 방향이 맞다.

1. **틀린 문제(X)는 연속 카운터를 끊는 칸막이다.** → 맞은 문제를 여러 덩어리로 쪼갤 수 있다.
2. **덩어리 하나에 `k-1` 개까지는 2배가 안 터진다.** → 정원 `group × (k-1)`.
3. **2배는 그 시점까지의 누적 점수를 곱한다.** → 2배가 **작은 점수에 걸리도록 앞쪽에 몰아야** 한다.

3번이 특히 좋다. 최소화 문제에서 "곱셈은 값이 작을 때 당해야 유리하다" 를 정확히 짚었다.
검증 삼아 `m=4, k=2, wrong=1` 을 손으로 돌려 봤다.

```
OOO X O  ->  1, 2(*2=4), 5, X, 6      = 6   (이 코드의 배치)
O X OOO  ->  1, X, 2, 3(*2=6), 7      = 7
OO X OO  ->  1, 2(*2=4), X, 5, 6(*2=12) = 12
```

앞쪽에 몰아넣는 쪽이 실제로 최소다.

## 개선점

### 1. (해결) 그리디가 최적인지 완전탐색으로 확인했다 — 맞다

이 리뷰의 초안은 "그리디 증명이 없으니 작은 n 완전탐색으로 대조하라" 였다. **2026-09-08 에 실제로 돌렸다.**
`n ≤ 12` 의 모든 `(n, m, k)` 조합 728건을 O/X 전 배치 완전탐색과 대조해 **불일치 0건**.
이성일의 대표 풀이(`이성일/week6/면접.java`)도 같은 728건에서 0건이다.
즉 **이 파일의 그리디는 정답이고, "실패" 의 원인은 배치 전략이 아니다.**

### 2. (중요) 점수가 int 를 넘길 수 있다 — 제약 확인 필요

`score *= 2` 가 반복되면 지수적으로 커진다. 2배가 31번만 일어나도 int 를 넘긴다. n 이 조금만 커져도 위험하다.
**→ 문제의 n·k 제약 확인 필요.** 제약에 따라 `long` 이나 모듈러 연산이 필요하고, 시험에서 틀렸다면
지금 남은 후보 중에서는 이 지점이 가장 유력하다.

## 요약

**틀린 문제를 칸막이로 본 것, 2배를 작은 점수에 걸리게 앞으로 몰아야 한다고 본 것** — 관찰이 맞았고
완전탐색 728건이 그것을 확인해 줬다. 알고리즘은 정답이다. 실패했다면 점수 자료형(int 초과)이나 입력 형식을
먼저 의심할 것. 그리디를 낼 때 **작은 입력 완전탐색 대조**를 붙이는 습관은 그대로 유효하다 —
이번엔 그게 "맞다" 를 15분 만에 증명했다.
